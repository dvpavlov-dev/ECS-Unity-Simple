Unity DOTS
справочник для первого проекта

Игра «Сборщик»: кубик ездит по полю и собирает монетки на время.
Восемь шагов. Код ты пишешь сам — здесь только то, из чего его собрать.

Как этим пользоваться. В каждом шаге написано, что должно заработать, какие файлы создать и какие конструкции для этого существуют. Готовых решений нет намеренно: концепция ECS укладывается в голове, когда сам решаешь, где лежат данные и кто их меняет. Если застрял на синтаксисе — он в таблицах. Если застрял на ошибке — приложение Б.

Порядок важен. Шаги устроены так, что после каждого игра запускается и что-то делает. Не прыгай вперёд: шаг 5 опирается на то, что в шаге 3 ты уже разобрался с бейкингом.

Чего здесь нет. Джобов, Burst, пулов, физики. Всё это в первом проекте только мешает: оно про производительность, а не про концепцию. Игра из восьми шагов работает на главном потоке и этого достаточно.

Unity 6000.x  ·  com.unity.entities 6.5  ·  URP
Сигнатуры даны для Entities 1.0 и новее; в версиях до 1.0 они выглядели иначе.

1Подготовка проекта

Цель: пустая сцена, в которой работает ECS, и открытые окна, показывающие сущности. Без них дальше придётся гадать.

Что сделать руками

  • Новый проект на шаблоне Universal 3D.
  • Package Manager → + → Add package by name → com.unity.entities.graphics. Он подтянет com.unity.entities сам. Ставить нужно именно graphics: без него сущности существуют, но не рисуются.
  • В сцене: правый клик в Hierarchy → New Sub Scene → Empty Scene, назови MainSubScene.
  • Открой Window → Entities → Hierarchy и Window → Entities → Systems. Первое окно показывает, что существует в игре, второе — какие системы работают и в каком порядке.
Главное правило всего проекта

Объект становится сущностью только если лежит внутри SubScene. В обычной сцене он выглядит в инспекторе точно так же, скрипт компилируется, ошибок нет — но бейкинг не запускается и сущности не появляется. Когда «система ничего не находит», первым делом смотри, внутри ли SubScene лежит объект.

Структура папок

Заведи сразу: Scripts/Components — структуры данных, Scripts/Authoring — мосты из сцены в ECS, Scripts/Systems — логика, Scripts/UI — обычные MonoBehaviour. Разделение не формальность: у этих четырёх видов кода разные правила, и держать их вперемешку больно.

Как проверить

Положи в SubScene обычный Cube. В окне Entities Hierarchy должна появиться сущность Cube; выдели её — справа видны её компоненты: LocalTransform, LocalToWorld и прочее. Если сущности нет, SubScene не запеклась: выдели её в Hierarchy и нажми в инспекторе Open, затем Close.

2Компоненты данных

Цель: описать, какие данные бывают в игре. Логики ещё нет, только структуры. Для понимания ECS это самый важный шаг.

Что создать

В Scripts/Components, по файлу на компонент: Speed, PlayerTag, CoinTag, Score, GameTimer, SpawnerData.

Из чего собирать

struct Speed : IComponentData
{ public float Value; }		 Компонент данных. Обязательно struct, обязательно публичные поля. Это не класс и не MonoBehaviour: нет методов, нет Start, нет ссылок на сцену.
struct PlayerTag : IComponentData { } Тег. Пустая структура. Нужна, чтобы отличать сущности в запросах — «возьми всех, у кого есть PlayerTag». Памяти не занимает.
struct Score : IComponentData
{ public int Value; }		 Синглтон. Технически обычный компонент; синглтоном его делает то, что в игре он существует ровно на одной сущности. Так хранят общее состояние: счёт, таймер, настройки.

Что можно класть внутрь

float, int, bool, enum
float2, float3, quaternion
Entity		 Можно. float3 и остальная математика — из Unity.Mathematics, не из UnityEngine. Entity — ссылка на другую сущность, внутри это просто пара чисел.
string, int[], List<T>,
GameObject, Transform, class		 Нельзя. Компонент должен быть blittable — простая память без ссылок. Ошибка появится не при компиляции, а позже, от IL-постпроцессора, и текст у неё невнятный.
Где ломается привычка из ООП

Хочется сделать один компонент Player со всеми полями: скорость, счёт, здоровье. Так делать не надо — и не из-за производительности, а потому что тогда каждая система зависит от всех данных сразу, и теряется главное свойство ECS: система видит ровно те поля, которые ей нужны.

Правило на первое время: один компонент — одна осмысленная величина. Позицию не описывай вообще, она уже есть (шаг 4).

Как проверить

Проверять пока нечего — убедись, что проект компилируется. Если в консоли ругань про blittable, внутри компонента остался класс, массив или строка.

3Игрок на сцене: authoring и Baker

Цель: кубик в SubScene превращается в сущность, у которой есть PlayerTag и Speed со значением, выставленным в инспекторе.

Бейкинг — это перевод сцены в сущности, он происходит в редакторе, до запуска игры. Authoring-компонент это обычный MonoBehaviour: он нужен только чтобы ты мог что-то потрогать в инспекторе. В игру он не попадает — в игру попадает то, что Baker из него сделал.

Что создать

Scripts/Authoring/PlayerAuthoring.cs, повесить на Cube внутри SubScene.

Каркас

public class PlayerAuthoring : MonoBehaviour
{
    public float Speed;          // видно в инспекторе

    class PlayerBaker : Baker<PlayerAuthoring>
    {
        public override void Bake(PlayerAuthoring authoring)
        {
            // здесь получить сущность и добавить ей компоненты
        }
    }
}

Из чего собирать

GetEntity(TransformUsageFlags flags) Сущность этого объекта. Вызывается внутри Bake. Флаг говорит, какие трансформные компоненты нужны: Dynamic — объект будет двигаться, Renderable — только рисуется и стоит на месте, None — чистые данные без позиции.
AddComponent(entity, new Speed { ... }) Добавить компонент со значением. Значения берутся из полей authoring.
AddComponent<PlayerTag>(entity) Добавить тег. Форма для пустых структур, значение передавать нечего.
GetEntity(authoring.Prefab, flags) Сущность другого объекта — понадобится в шаге 5 для префаба. Возвращает Entity, который можно положить в компонент.
Две ловушки, обе тихие

Забыл AddComponent — ошибки не будет никакой. Система просто не найдёт ни одной подходящей сущности и будет молча работать впустую. Это самая частая причина «ничего не происходит, но и не падает».

Неверный TransformUsageFlags — если поставить Renderable объекту, который должен двигаться, у сущности не будет LocalTransform, и запрос из шага 4 её не увидит. Для игрока нужен Dynamic.

Как проверить

Entities Hierarchy → выдели сущность кубика. В списке её компонентов должны быть PlayerTag и Speed, причём у Speed видно значение из инспектора. Поменяй значение в инспекторе — число в окне сущностей должно измениться сразу, без запуска игры. Это и есть бейкинг.

4Движение по WASD

Цель: кубик едет по нажатию клавиш, упираясь в границы поля. Первая система.

Система — это struct, который Unity находит сам и вызывает каждый кадр. Регистрировать его нигде не нужно, достаточно объявить. Слово partial обязательно: генератор кода дописывает в систему свою половину, и без partial будет ошибка компиляции.

Каркас

public partial struct PlayerMoveSystem : ISystem
{
    public void OnCreate(ref SystemState state) { }   // один раз, до игры
    public void OnUpdate(ref SystemState state) { }   // каждый кадр
    public void OnDestroy(ref SystemState state) { }  // при выключении
}

Все три метода необязательны: у ISystem есть пустые реализации по умолчанию, лишние можно не писать.

Позиция, поворот, масштаб

LocalTransform Трансформ сущности. Отдельный компонент писать не надо, он появляется сам при флаге Dynamic. Поля: Position (float3), Rotation (quaternion), Scale (float — один, а не три).
LocalTransform.FromPosition(float3) Создать трансформ. Есть также FromPositionRotation, FromPositionRotationScale, LocalTransform.Identity.

Перебор сущностей

foreach (var (a, b) in SystemAPI
  .Query<RefRW<LocalTransform>,
         RefRO<Speed>>())		 Основной цикл ECS. Перебирает все сущности, у которых есть все перечисленные компоненты. Остальные не попадут.
RefRW<T> → .ValueRW
RefRO<T> → .ValueRO		 Чтение и запись. RW — собираешься менять, RO — только читать. Ставь RO везде, где можно: это не стиль, а информация для планировщика.
.WithAll<PlayerTag>() Фильтр по тегу. Дописывается после Query. Нужен, когда сам компонент в цикле не используется, а отличить сущности надо. Есть ещё WithNone<T>(), WithAny<T>().
.WithEntityAccess() Добавляет саму сущность последним элементом кортежа. Нужно, когда её собираешься удалить или изменить — см. шаг 6.
SystemAPI.Time.DeltaTime Время кадра. Не Time.deltaTime из UnityEngine. Умножай на него любое движение, иначе скорость будет зависеть от частоты кадров.

Ввод и математика

Input.GetAxis("Horizontal")
Input.GetAxis("Vertical")		 Оси WASD и стрелок, от −1 до 1. Это обычный UnityEngine, и работает он только на главном потоке — то есть прямо в OnUpdate. Внутрь джобы его вынести нельзя.
math.clamp(v, min, max)
math.normalize(v)
math.lengthsq(v)		 Математика из Unity.Mathematics. Для границ поля нужен clamp по X и Z.
Диагональ едет быстрее

Если складывать ввод по осям напрямую, при двух нажатых клавишах длина вектора будет 1.41 вместо 1, и по диагонали кубик поедет на 41% быстрее. Нормализуй вектор ввода — но только когда он не нулевой: math.normalize от нуля даёт NaN, а NaN в позиции убивает сущность навсегда.

Как проверить

Кубик едет по WASD с той скоростью, что стоит в инспекторе, и не уезжает за край поля. Зажми две клавиши: по диагонали скорость должна быть такой же, как по прямой.

5Спавн монеток

Цель: раз в N секунд в случайном месте поля появляется монетка. Здесь впервые создаются сущности во время игры.

Сущность нельзя просто создать посреди перебора: создание и удаление меняют структуру памяти и ломают цикл, внутри которого ты находишься. Поэтому команды складывают в буфер и проигрывают после.

Что создать

Префаб монетки (Cube поменьше, свой материал) + CoinAuthoring с CoinTag. Пустой объект Spawner в SubScene + SpawnerAuthoring с полем public GameObject CoinPrefab. Система CoinSpawnSystem.

Префаб тоже надо запечь

Положить GameObject в компонент нельзя. В Baker спавнера вызови GetEntity(authoring.CoinPrefab, TransformUsageFlags.Dynamic) — вернётся Entity, вот его и храни в SpawnerData.Prefab. Сам префаб при этом не обязан лежать в сцене.

Создание сущностей

state.EntityManager
  .Instantiate(prefabEntity)		 Копия префаба, немедленно. Возвращает Entity, которому можно сразу задать позицию. Простой путь, годится, пока создаёшь по одной сущности вне перебора.
var ecb = new EntityCommandBuffer(
  Allocator.Temp);
ecb.Playback(state.EntityManager);
ecb.Dispose();		 Буфер команд. Собирает действия и выполняет их все сразу в момент Playback. Так создают и удаляют сущности, находясь внутри перебора.
ecb.Instantiate(prefab)
ecb.DestroyEntity(entity)
ecb.SetComponent(e, value)
ecb.AddComponent(e, value)		 Команды буфера. Выполняются не сразу, а при Playback. Instantiate возвращает «обещание» сущности — ему можно задавать компоненты, хотя её ещё нет.
state.EntityManager
  .SetComponentData(e, value)		 Задать компонент немедленно. Парный GetComponentData<T>(e). Внутри перебора использовать нельзя — только до или после.

Таймер и случайность

Unity.Mathematics.Random
Random.CreateFromIndex(uint seed)
rnd.NextFloat(min, max)
rnd.NextInt(min, max)		 Случайные числа для ECS. Это структура с состоянием: её надо хранить в компоненте и возвращать обратно после использования, иначе каждый кадр выпадет одно и то же число. UnityEngine.Random в ECS не используют.
поле float Timer в компоненте Как отсчитывать время. Своей памяти у системы нет — точнее, есть поля структуры, но хранить состояние игры в них неправильно. Прибавляй DeltaTime к полю компонента, при достижении порога спавни и вычитай порог.
Состояние системы живёт в компонентах

Соблазн объявить private float _timer полем системы. Так делать не надо: система концептуально не владеет данными, она их только обрабатывает. Таймер — это данные игры, его место в SpawnerData. То же про Random.

Как проверить

Монетки появляются в разных местах с нужным интервалом, и число сущностей в Entities Hierarchy растёт. Если все появляются в одной точке — не вернул состояние Random обратно в компонент.

6Подбор монеток и счёт

Цель: когда игрок подъезжает к монетке, она исчезает, счёт растёт на единицу.

Здесь появляется задача, непривычная после ООП: нужно сравнить игрока с каждой монеткой, то есть совместить два разных перебора. Прямого способа нет и это нормально — позиция игрока берётся до цикла, одним запросом.

Что создать

Система CoinPickupSystem. Сущность-синглтон со Score: либо отдельный пустой объект в SubScene с authoring-компонентом, либо создать её в OnCreate системы (см. ниже).

Синглтоны

SystemAPI.GetSingleton<Score>() Прочитать синглтон. Возвращает копию — изменения в ней никуда не попадут. Бросает исключение, если сущностей не ровно одна.
SystemAPI.GetSingletonRW<Score>()
  .ValueRW.Value++		 Изменить синглтон. Именно это нужно для счёта. Самая частая ошибка новичка — менять результат GetSingleton и удивляться, что ничего не меняется.
SystemAPI.TryGetSingleton<T>(out T v) Безопасный вариант — false вместо исключения, если синглтона нет.
SystemAPI.GetSingletonEntity<T>() Сама сущность синглтона, а не его значение.
state.EntityManager.CreateEntity()
  + AddComponent<Score>(e)		 Создать синглтон кодом, в OnCreate. Удобно, когда в инспекторе настраивать нечего: не нужен ни объект в сцене, ни authoring.

Поиск соседей и удаление

math.distancesq(a, b) Квадрат расстояния. Сравнивай с квадратом радиуса: distancesq < r * r. Корень не считается, а для сравнения он и не нужен.
.WithEntityAccess() Нужен здесь обязательно — чтобы получить Entity монетки и передать его на удаление.
ecb.DestroyEntity(entity) Удалить сущность после перебора. Напрямую EntityManager.DestroyEntity внутри foreach вызывать нельзя.
Как получить позицию игрока внутри цикла по монеткам

Не вкладывай один SystemAPI.Query в другой. Правильно: до цикла одной строкой достать трансформ игрока — через запрос с WithAll<PlayerTag>() или через синглтон, если игрок один, — положить в локальную переменную float3, и дальше перебирать монетки, сравнивая с ней.

Как проверить

Монетка исчезает при наезде. Значение Score в Entities Hierarchy растёт — выдели сущность со счётом и смотри на него во время игры. На экране его ещё нет, это следующий шаг.

7Счёт и таймер на экране

Цель: счёт и остаток времени видны на экране. Здесь ECS соединяется с обычным Unity.

UI в DOTS не живёт — Canvas, Text и кнопки остаются обычными MonoBehaviour. Значит нужен мост: скрипт, который из Update заглядывает в мир сущностей и переписывает текст.

Что создать

Canvas с двумя TextMeshProUGUI. Scripts/UI/GameHud.cs — обычный MonoBehaviour на Canvas. Систему GameTimerSystem, которая вычитает DeltaTime из GameTimer.

Доступ к ECS из MonoBehaviour

World.DefaultGameObjectInjectionWorld
  .EntityManager		 Вход в мир сущностей из обычного кода. Мир один, создаётся автоматически.
entityManager.CreateEntityQuery(
  ComponentType.ReadOnly<Score>())		 Запрос, который потом можно спрашивать каждый кадр. Создавать его надо один раз в Start и хранить в поле.
query.GetSingleton<Score>() Прочитать значение. У запроса свои методы, похожие на SystemAPI.
query.CalculateEntityCount() Сколько подходящих сущностей. Так выводят «монеток на поле: N» без всякого счётчика. Полезно и как проверка перед чтением синглтона.
query.CompleteDependency() Дождаться систем, которые пишут эти компоненты. В простом проекте, где всё на главном потоке, не нужно — но привыкай ставить: как только появятся джобы, без этой строки чтение падает каждый кадр.
query.ToComponentDataArray<T>(
  Allocator.Temp)		 Все значения массивом, если нужно не одно. Массив надо освобождать: .Dispose() или using.
Два правила моста

Запрос создаётся в Start, не в Update. Создание запроса — операция недешёвая, а делать её 60 раз в секунду незачем.

Порядок загрузки не гарантирован. MonoBehaviour может стартовать раньше, чем запеклась SubScene, и синглтона в первый кадр ещё не будет. Проверяй CalculateEntityCount() == 1 перед чтением, иначе поймаешь исключение на старте.

Как проверить

Счёт на экране совпадает с тем, что показывает Entities Hierarchy. Таймер убывает. Запусти и останови игру несколько раз подряд — исключений в первом кадре быть не должно.

8Конец игры и перезапуск

Цель: время вышло — игра останавливается, появляется окно с результатом и кнопкой. Кнопка возвращает всё в начальное состояние.

Нужен флаг, который видят и системы, и UI. Это синглтон с состоянием — тот же приём, что со счётом, но теперь его читают почти все.

Что создать

Компонент GameState с полями bool IsOver, bool RestartRequested. Систему GameRestartSystem. Панель Game Over с кнопкой, скрипт на ней пишет RestartRequested = true.

Остановка систем

if (SystemAPI.GetSingleton<GameState>()
      .IsOver) return;		 Самый простой способ. Первая строка в OnUpdate каждой системы, которую надо приглушить: движение, спавн, подбор, таймер. Понятно и отлаживается легко.
state.Enabled = false; Выключить систему насовсем. Годится для систем, которые делают работу один раз в OnCreate. Для игровой логики не подходит: включить обратно сложнее, чем кажется.
state.RequireForUpdate<T>() Не вызывать OnUpdate, пока нет такого компонента. Ставится в OnCreate. Удобно, но опасно: если компонент пропал, система молча не работает и в консоли ничего нет.

Сброс состояния

query.ToEntityArray(Allocator.Temp)
→ em.DestroyEntity(array)		 Удалить все монетки. Сначала собрать массив сущностей, потом удалить — внутри перебора удалять нельзя.
em.DestroyEntity(EntityQuery) Есть и такая перегрузка, но она требует, чтобы в запрос попали все связанные дочерние сущности, иначе бросает ArgumentException. С составными префабами проще через массив.
em.SetComponentData(e, value) Вернуть значения. Счёт в ноль, таймер на полную, позицию игрока в центр, IsOver = false.
Что тут обычно забывают

Сбросить таймер спавнера. Он остался от прошлой партии, и первая монетка либо появится мгновенно, либо через полный интервал вместо нужного. Правило общее: при перезапуске возвращай в исходное всё изменяемое состояние, а не только то, что видно на экране.

Как проверить

Время вышло → кубик не едет, монетки не появляются, видно окно с результатом. Кнопка → поле чистое, счёт ноль, таймер полный, игрок в центре. Пройди три партии подряд, не выходя из Play: вторая и третья должны быть идентичны первой.

Куда идти дальше

Когда это заработает, в игре есть все базовые приёмы ECS: данные в компонентах, логика в системах, бейкинг из сцены, отложенные команды, синглтоны, мост в UI. Следующие темы по порядку полезности: IJobEntity и [BurstCompile] (та же логика, но в несколько потоков), IEnableableComponent и пулы (перестать создавать и удалять сущности каждую секунду), группы систем и явный порядок через [UpdateBefore], буферы (IBufferElementData) для передачи событий в UI и звук.

Приложение Б. Ошибки и что они значат

Главная часть справочника. Половина времени новичка уходит на расшифровку этих сообщений.

Не компилируется
...must be declared partial У системы нет слова partial. Генератор кода дописывает в неё свою часть, и без этого слова не может.
field of type ... is neither
primitive nor blittable		 В IComponentData лежит класс, массив, строка или List. Убрать; для переменной длины — буфер.
The type or namespace 'float3'
could not be found		 Нет using Unity.Mathematics;. Остальные обычные: Unity.Entities, Unity.Transforms, Unity.Collections.
Падает в игре

...but found 2 Синглтон запёкся дважды — обычно authoring висит и на объекте, и на префабе, либо объект продублирован в сцене.
Attempt to add duplicate

has been destroyed		 Держишь Entity удалённой сущности. Проверяй EntityManager.Exists(e), либо не удаляй дважды: при двух попаданиях в один кадр DestroyEntity вызовется два раза.

Приложение В. Чем смотреть, что происходит

В ECS нельзя просто нажать на объект в Hierarchy и увидеть состояние. Инструменты другие, и без них отладка превращается в угадывание.

Window → Entities → Hierarchy Главное окно. Все сущности мира и их компоненты со значениями, живьём во время игры. Первое место, куда смотреть, когда «не работает». Есть поиск по имени компонента.
Window → Entities → Systems Список систем в порядке выполнения, с галочками включения и временем работы. Видно, попала ли твоя система в нужную группу и вызывается ли вообще.
Window → Entities → Components Все типы компонентов в проекте и сколько сущностей имеет каждый. Быстрый ответ на «запеклось ли оно вообще».
Window → Entities → Archetypes Наборы компонентов и память под них. Для первого проекта любопытно, но не обязательно.
Инспектор SubScene: Open / Close Переключение режима. Open — правишь объекты, сущностей нет. Close — объекты запекаются в сущности. Многие «необъяснимые» проблемы сводятся к забытому Open.
Debug.Log в OnUpdate Работает, пока система без [BurstCompile] и логика не в джобе. Внутри Burst-кода логировать нельзя — это одна из причин, почему Burst в первом проекте только мешает.
Порядок разбора любой поломки
  • Есть ли ошибка в консоли. Если есть — приложение Б, не угадывай.
  • Существует ли сущность. Entities Hierarchy.
  • Те ли у неё компоненты и те ли значения. Там же.
  • Вызывается ли система. Entities → Systems, или Debug.Log.
  • Находит ли запрос хоть что-то. CalculateEntityCount() в лог.

Четыре из пяти поломок новичка находятся на втором или третьем пункте, и оба проверяются глазами за десять секунд.
